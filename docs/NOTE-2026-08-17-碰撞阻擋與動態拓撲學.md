# 0. 結論先講

### ① 撞牆傷害在本專案**沒有可用的數值** —— 整除性把它變成懸崖，不是曲線

🟡 撞牆傷害 `c` 只有在**穿越刀數階梯**時才有價值。門檻是：

```
c  ≥  H mod D        （當 D ∤ H）
c  ≥  D              （當 D ∣ H）      ← 本專案落在這一格
```

🟢 而 `units.txt` **刻意**把整個敵人階梯做成 40 的倍數
（「Momotaro deals 60-20 = 40, so HP fixes EAtK exactly: 80 → 2 hits, 120 → 3, 160 → 4, 240 → 6」）。
**`D ∣ H` 對整個階梯成立，所以門檻是完整的 40 —— 一次普攻的全額。**

| 撞牆傷害 | 對 80 HP 小耗（桃太郎 40/刀） | 判定 |
|---|---|---|
| 24（AP 等值換算出的「公平」值，§4.1） | 80 → 56，`ceil(56/40)` 仍是 **2 刀** | **買到 0** |
| 39 | 80 → 41，仍是 **2 刀** | **買到 0** |
| **40** | 80 → 40，變成 **1 刀** | 穿越，但 3 AP 買到 40 傷 = **擊退直接壓過 5 AP 普攻** |

> 🔴 **沒有中間值。** 低於 40 是零，等於 40 就支配。
> **「刻意的整除性」與「碰撞傷害」是互斥的兩個設計選擇，不能同時要。**

### ② 阻擋是階梯函數，不是曲線 —— 沒有 ZOC 時「擋一半」的價值恰好是 0

🟢 `CanUnitEnter(c) = Map.IsPassable(c) && !IsOccupied(c)`（`BattleState.cs:315`，OD-02 + OD-03）——
單位確實阻擋移動。但**沒有 ZOC、沒有借機攻擊**，所以：

```
ΔT_clash(路寬 W, 肉身數 B)  =  { 擊殺阻擋者所需回合   if B ≥ W   （完全封閉）
                              { 0                    if B < W   （直接走過去）
```

> 🔴 **在 W=2 的隘口放 1 個正守，延後的回合數是 0，不是「一半」。**
> 防守價值是地圖的性質，不是正守的性質。

### ③ 直線推撞**可證明無環**，所以連鎖推撞是安全的 —— 而且它繞過了整除性問題

🟡 推撞方向沿 actor→target 軸固定，每一步嚴格單調遞增（或遞減）於單一座標軸，
**座標不可能重複 → 不存在 cycle → 必在 `O(max(W,H))` 步內終止**（§4.5 的證明）。

> 🟡 **而且連鎖是「位移」不是「傷害」，所以它完全不受整除性懲罰。**
> 把 B 推去撞 C、把 C 撞進深坑，價值是一次完整擊殺 ——
> **這給你 ITB 的手感，而不需要碰撞傷害這個數字。**

### ④ 🔴 順帶確認一個**會讓戰鬥永遠不結束**的缺陷

🟢 `BattleSimulator.cs:733-734`：

```csharp
if (r.Spawned || r.Faction != faction || r.Turn != state.TurnIndex) continue;
if (!state.CanUnitEnter(r.Position)) continue;   // blocked this turn; try again next round
```

**註解說「下回合再試」，但程式碼做不到**：第一行要求 `r.Turn == TurnIndex` 精確相等，
所以下一回合 `TurnIndex` 已經前進，這個增援**永遠不會再生成**，而 `r.Spawned` 永遠是 `false`。

🟢 於是 `HasPendingReinforcements`（`BattleState.cs:275-280`，只看 `!Spawned`）**永遠回傳 true**，
而 `CheckBattleEnd`（`BattleSimulator.cs:825`）要求
`CountLiving(Enemy) == 0 && !HasPendingReinforcements(Enemy)` ——

> 🔴 **玩家殺光全部敵人，戰鬥不會結束。`rout` 勝利在該場永遠無法達成。**
> 🟢 而 R-WIN-04 明文「沒有回合數上限、沒有平手」，所以規則層沒有任何逃生口。
>
> 觸發條件不苛刻：**任何單位**（含敵方自己）在該回合站在增援格上即可，
> 而跑分工具有 15% 均勻雜訊。詳見 §6。

# 1. 現況盤點 🟢

## 1.1 擊退（Push）

`BattleSimulator.cs:447-528`：

| 性質 | 現況 |
|---|---|
| 距離 | **固定 1 格**，沿 actor→target 軸（`TryPushDestination`） |
| 幾何 | 四鄰接，**必須同行或同列**；對角線直接拒絕 |
| 目的地被擋 | 🔴 **拒絕執行（Reject）**，不扣 AP、不產生任何 Effect |
| 碰撞傷害 | ❌ **完全沒有**。撞牆 0 傷、撞人 0 傷 |
| 連鎖 | ❌ **沒有**。B 永遠碰不到 C |
| 免疫 | `ImmuneToPush`：正守（GDD 金剛王菩薩）、玄真、`e2_anchor` |
| 推入深坑 | ✅ `ResolveHazard` 在位移後立即結算 |

🟢 拒絕而非空放的理由寫在 `BattleSimulator.cs:475-477`：
「spending AP for no visible change is the worst possible feedback」。

## 1.2 地形與即死地塊

🟢 `terrain.txt`：`Open(1) / Road(1) / Forest(2) / Highland(2) / Blocking(阻擋) / Mire(3, gym-only) / Chasm(1, lethal)`

| 規則 | 內容 |
|---|---|
| **R-TERR-07** | `lethal=true` 的格子，**任何單位位移或移動後停在其上立即死亡** |
| **R-TERR-08** | 即死格是**可通行**的；載入器拒絕 `blocks=true lethal=true` |
| **R-TERR-09** | 🔴 **尋路不得把即死格列為可達目的地** —— 單位永不自願走入，只有位移放得進去 |
| **R-TERR-10** | 即死**不經過傷害公式**：不受 DEF、Guard、任何減傷影響 |

> 🟢 R-TERR-09 的理由寫得很明白，且**不是玩家體驗，是量測有效性**：
> 跑分工具的 15% 雜訊是均勻抽樣，若可達集合含即死格，單位會隨機自殺，該地圖所有量測失效。
>
> 🟢 Chasm 成本刻意設為 1，「so that nothing about the AP economy changes when one is on the map」。
> 且**刻意附加在 terrain 清單最後**，因為 `TerrainDef.Index` 由宣告順序決定，插在中間會靜默改變所有已量測地圖。

## 1.3 判定點是「停下來的那一格」 🟢

> R-TERR-07 註記：「⚠️ 判定點是停下來的那一格，不是路徑經過的每一格。
> 規則層的移動是一次性換位（路徑僅用於計價），逐格判定會憑空引入一個其他規則都沒有的分步模型。」

🟡 **這條對本主題極重要**：它意味著**「推過一個深坑」不會死，只有「停在深坑」才會死。**
現行推撞固定 1 格，所以兩者等價；**任何多格推撞的提案都必須先回答這一條。**

# 2. 核心衝突：位移的計價單位是 tempo，不是傷害

傷害與位移在戰棋裡是兩種不同貨幣，而**只有傷害受整除性懲罰**：

| 手段 | 作用於 | 受刀數階梯影響？ |
|---|---|---|
| 普攻、碰撞傷害、反擊 | **分子** `H`（敵人剩餘 HP） | 🔴 **是** —— 不穿越階梯就等於 0 |
| 破甲（−20 DEF） | **分母** `D`（每刀傷害） | ⚠️ 部分 —— 改變階梯本身 |
| 擊退、遲滯、阻擋、深坑 | **完全在階梯之外**（位置與時間） | ✅ **否** |

> 🟡 **這是貫穿本專案的一條結構原則，值得單獨記住**：
> **在一個刻意整除的數值系統裡，位移永遠優於傷害。**
>
> 🟢 這也回頭解釋了 T1 §4.5 的發現（正守反擊 13 傷穿不過任何階梯）
> 與 `units.txt:338-345` 對破甲的分析（「a break that does not cross a step buys nothing」）——
> **三件事是同一條定律的三個實例。**

## 3.1 ITB 的「1 傷」為什麼有效，而本專案抄不動 🟡

🔵 ITB 的 Vek HP 是 1–6，玩家每刀 1–3。關鍵在於**HP 不是傷害的整數倍**：

| Vek | HP | 玩家每刀 | 原刀數 | 撞 1 傷後 | 穿越？ |
|---|---|---|---|---|---|
| Firefly | 3 | 2 | 2 | `ceil(2/2)` = **1** | ✅ |
| Alpha Firefly | 5 | 2 | 3 | `ceil(4/2)` = **2** | ✅ |
| Scarab | 2 | 2 | 1 | — | 已是 1 刀 |

> 🔵 **ITB 的碰撞傷害幾乎每次都穿越階梯，因為 `H mod D = 1` 而碰撞傷害恰好是 1。**
> 🟢 本專案 `H mod D = 0`（80 mod 40、120 mod 40、160 mod 40 全部是 0），
> **所以同樣的機制在這裡的期望價值是 0。**
>
> 🔴 **這不是「ITB 的數字要縮放」的問題，是「ITB 的階梯性質與本專案相反」。**
> 抄數字會失敗，抄比例也會失敗。

## 3.2 FE 的「1 人擋 N 人」來自 ZOC，不是肉身 🔵🟡

> 🔵 傳統戰棋的 body-blocking 之所以能用 1 個人癱瘓一整支行軍，
> 是因為 **ZOC 讓一個單位的影響力覆蓋到它站的那格以外**。
>
> 🟢 本專案沒有 ZOC（[H20](NOTE-2026-08-15-移動力射程與地圖幾何.md) 仍是假說，紙上模型都還沒做），
> 所以**一個單位的影響力嚴格等於它佔的那一格**。
> **這就是 §0② 的階梯函數的來源。**

# 4. 數學模型

## 4.1 位移-傷害折算：先給錯的答案，再給對的 🟡

**天真解（AP 等值）**：擊退在純傷害上不輸普攻的條件是

```
c / pushCost  ≥  D_attack / attackCost
c  ≥  D_attack × (pushCost / attackCost)
```

| 配置 | 計算 | 天真門檻 |
|---|---|---|
| `Momotaro_B`（攻 40 @ 5 AP，推 @ 3 AP） | 40 × 3/5 | **c ≥ 24** |
| 出貨 `momotaro_push`（攻 40 @ 4 AP，推 @ 1 AP） | 40 × 1/4 | **c ≥ 10** |

**這個答案是錯的**，因為傷害只在穿越 `ceil` 階梯時才存在。正確門檻：

```
ceil((H − c) / D)  <  ceil(H / D)
  ⟺   c  ≥  H − D·(ceil(H/D) − 1)
  ⟺   c  ≥  H mod D      （D ∤ H）
       c  ≥  D           （D ∣ H）
```

🟢 帶入本專案（`D` = 桃太郎 40，`H` ∈ {80, 120, 160, 240}，全部 `mod 40 = 0`）：

```
真實門檻  c ≥ 40      而天真門檻只有 24
                      —— 相差 67%，而且 24 買到的是 0 而不是「少一點」
```

> 🔴 **這是本檔最重要的算式。** 在整除的數值系統裡，
> 「AP 等值折算」這種直覺定價法會系統性地把價格訂在**買到零的區間**。
> T1 §4.5 的反擊（13 傷）與本節的撞牆傷害（24）**是同一個錯誤的兩個實例。**

## 4.2 那撞牆傷害到底該定多少？🟡

| 候選 `c` | 對 80/120/160 HP 階梯 | 對 3 AP 擊退的意義 |
|---|---|---|
| 1–39 | 全部不穿越 | **買到 0**。擊退仍是純位移動詞 |
| **40** | 全部少一刀 | 3 AP 買到 40 傷；普攻 5 AP 買到 40 傷 → **擊退嚴格支配普攻**（還附贈位移） |
| 41+ | 同上 | 更糟 |

> 🟡 **不存在一個「剛好」的值。** 這是階梯的必然結果，不是調參不夠仔細。
>
> **三條出路，二選一（第三條不建議）**：
>
> | | 做法 | 代價 |
> |---|---|---|
> | **A** | **不加碰撞傷害。** 擊退維持純位移（深坑、重定位、連鎖） | 🟢 零成本，維持現況。**本檔建議這條** |
> | **B** | 打破敵人 HP 的整除性（例如 80 → 70、100） | 🔴 會推翻 `units.txt` 的整個 kill-target ladder 與所有已量測的基準 |
> | **C** | 加 40 傷 | 🔴 擊退支配普攻，回到「唯一最優解」的老問題 |

## 4.3 深坑推殺的效率比與幾何可用性 🟢🟡

```
深坑推殺 AP 效率  =  (RH × attackCost) / pushCost
```

🟢 對 `sc_bruiser`（180 HP，桃太郎 40/刀 → RH 5 → 20 AP）：

| 推撞定價 | 效率比 |
|---|---|
| 出貨 1 AP | **20×** |
| `Momotaro_B` 3 AP | **6.7×** |

🟢 `units.txt:394` 自己就是這樣寫的：「sc_bruiser 180 HP → Momotaro B's push (the chasm skips all 180 of it)」。

**但幾何可用性極低，這才是真正的平衡機制** 🟡：

四鄰接 ＋ `pushRange 1` ＋ 推向 actor→target 的延長線 ⟹ 對每一個深坑格，
「可推殺的 (攻擊者格, 目標格)」配對**恰好有 4 組**（目標在深坑的四個鄰格，攻擊者在目標的正對面）。

```
一張有 k 個深坑格的地圖  ->  至多 4k 種推殺構型
```

> 🟡 **所以深坑推殺的設計旋鈕是「深坑位置」，不是「擊退定價」。**
> 20× 的效率比看起來失衡，但它需要玩家把敵人**誘導到 4k 個特定格之一**，
> 且自己站在唯一的對面格。
> 🟢 而 [OD-16](OPEN-DECISIONS.md#od-16)（敵人主動接敵）讓誘導變得可行 —— 這是一個良性的耦合。

## 4.4 隘口阻擋效率 ΔT_clash 🟢🟡

**模型**：路寬 `W`（隘口的並行通行格數）、我方投入肉身 `B`、敵方每回合攻擊次數 `APT_e = 2`。

```
ΔT_clash(W, B)  =  { ceil( RH_blocker / (W × APT_e) )   if B ≥ W
                   { 0                                   if B < W
```

**`B < W` 時恰好為 0**，因為沒有 ZOC、沒有借機攻擊 —— 敵人直接從空著的通道走過去，不付任何代價。

### 各角色封鎖 W=1 隘口的延後回合數 🟢

小耗 ATK 100，`傷害 = max(1, 100 − DEF)`，`RH = ceil(HP / 傷害)`，1 個攻擊者 × 2 刀/回合：

| 阻擋者 | HP | DEF | 每刀受傷 | RH | **ΔT_clash** | 加 Guard（3 AP，傷害減半） |
|---|---|---|---|---|---|---|
| **正守** | 435 | 70 | 30 | 15 | **7.5 回合** | 🔴 **14.5 回合** |
| 桃太郎 | 300 | 50 | 50 | 6 | 3.0 回合 | 6.0 回合 |
| 玄真 | 220 | 35 | 65 | 4 | 2.0 回合 | 4.0 回合 |
| 影丸 | 195 | 30 | 70 | 3 | 1.5 回合 | 3.0 回合 |

> 🟡 **正守封鎖 W=1 隘口 = 7.5 回合，是影丸的 5 倍。這是他的防守價值第一次被量化。**
>
> 🟡 **而且他應該永遠 Guard**：他 ATK 33 對小耗只有 13 傷（T1 §4.5 已證明穿不過階梯），
> 所以站樁時他的攻擊價值近乎 0，而 3 AP 的 Guard **直接把 ΔT_clash 翻倍到 14.5 回合**。
> **「正守擋路時該做什麼」有唯一正解，而且不是攻擊。**

### 路寬與隊伍成本 🟡

```
封鎖成本  =  W / 4  的隊伍（4 人隊）
```

| W | 需要肉身 | 佔隊伍 | 判定 |
|---|---|---|---|
| **1** | 1 | 25% | ✅ 唯一實用的路寬 |
| **2** | 2 | 50% | ⚠️ 昂貴；1 人 = 0 延後 |
| **3** | 3 | 75% | 🔴 不可行 |

> 🟡 **關卡設計約束：想讓阻擋成為有意義的決策，隘口路寬必須是 1 或 2。**
> W ≥ 3 時封鎖不可行，而阻擋機制在該地圖上等於不存在。

### 移動力 M 的角色：它作用在另一個加項 🟡

```
T_total  =  T_arrival  +  ΔT_clash
            ↑ M 影響這項      ↑ 阻擋影響這項      —— 兩者獨立相加
```

🟢 `attackCost 4`、AP 8、平地 1 AP/格 ⟹ **「移動後還能攻擊」的上限是 4 格，與 MOVE 屬性無關**（`d + 4 ≤ 8`）。

🟢 影丸【遲滯】使移動 +1 AP/格 ⟹ 平地 2 AP/格 ⟹ `2d + 4 ≤ 8` ⟹ **上限降為 2 格**。

| | 威脅半徑（近戰 range 1） | 菱形涵蓋格數 `2r²+2r+1` |
|---|---|---|
| 正常 | 4 + 1 = **5** | **61 格** |
| 遲滯後 | 2 + 1 = **3** | **25 格** |

> 🟡 **遲滯把敵人的威脅面積砍掉 59%，而且這個效果與 MOVE 屬性完全無關 ——
> 它對 MOVE 3 和 MOVE 5 的單位一樣有效。**
>
> 🔴 **而威脅半徑正是 T2 §5.1 的 I2（靜態威脅圈）要顯示的東西。**
> **遲滯是全隊唯一一個效果直接畫在威脅圈上、玩家一眼看得見的動詞。**
> T2 說嘲諷是「把 CF(目標) 鎖成 1.0」的資訊動詞；**遲滯是把威脅面積砍半的資訊動詞。**

## 4.5 連鎖推撞：終止性證明與決定論要求 🟡

**命題**：直線推撞鏈必定終止，且不存在 cycle。

**證明**：推撞方向 `(sx, sy)` 由 `TryPushDestination` 固定為單一軸上的 ±1
（🟢 `BattleSimulator.cs:515-528`，對角線直接回傳 false）。鏈上第 `n` 個單位的目的地為
`p₀ + n·(sx, sy)`。該座標在該軸上**嚴格單調**，故任兩步的座標必不相同 ⟹ **無 cycle**。
又地圖有界（R-GRID-04），故鏈長 ≤ `max(Width, Height)` ⟹ **必定終止**。∎

> 🟡 **這比 ITB 的問題簡單得多。** ITB 一次結算整個 Vek 階段、含多個同時位移，
> 必須明確定義結算順序；本專案一次只執行一個 `PushCommand`，且方向固定，
> **所以連鎖推撞在這裡是一個可證明安全的機制。**

**若要實作，四條決定論要求** 🟡：

| # | 要求 | 理由 |
|---|---|---|
| **C1** | **先算完整條鏈，再一次位移**（不要邊走邊推） | 邊走邊推會讓「前一個單位是否已讓開」影響後一個的合法性，產生順序相依 |
| **C2** | **位移順序由遠而近**（鏈尾先動） | 由近而遠會撞到還沒讓開的單位。這是位置決定的順序，不是 id 決定的 |
| **C3** | **全部位移完成後，再由遠而近結算 hazard** | 鏈中段有人掉進深坑會改變鏈的阻塞狀態；先算幾何、後算死亡，才有唯一解 |
| **C4** | **每個單位在單一 `PushCommand` 內最多被位移一次** | 防止重複處理；配合 C1 的「先算鏈」自然成立 |
| **C5** | **鏈尾被擋 ⟹ 整條鏈 Reject**（沿用現行語意） | 🟢 與 `BattleSimulator.cs:475-477` 的既有理由一致：不要花 AP 換取零可見變化 |

**A4 影響** 🟡：連鎖推撞**不需要任何新的 state 欄位** ——
位置已經在 hash 裡（`StateHasher.cs:36-37`）。它會改變 golden hash（行為變了），
但**不改變 state schema**，屬於最便宜的一類規則變更。

> ⚠️ 仍然是規則層變更，依 [documentation-rules](99-governance/documentation-rules.md) 須登錄 OD。**本檔不裁決。**

# 5. 對本專案的具體指引

## 5.1 直接回答三個問題 🟡

### Q1：撞牆傷害該定多少？

> **建議不要加。** §4.1–4.2 證明在 `D ∣ H` 的階梯上不存在「剛好」的值：
> 39 以下買到 0，40 以上讓 3 AP 擊退支配 5 AP 普攻。
> **要讓被擋的推撞「有事發生」，正確的動詞是連鎖（位移），不是傷害。**

### Q2：如何在 Ediki.Core 引入碰撞與阻擋而維持 A4 與簡潔性？

| 提案 | 新 state 欄位 | A4 | 複雜度 |
|---|---|---|---|
| **連鎖推撞**（§4.5 的 C1–C5） | ❌ **不需要** | 會變（行為變） | 低 —— 一個迴圈 ＋ 一條終止性證明 |
| 碰撞傷害 | ❌ 不需要（HP 已在 hash） | 會變 | 低，但 §4.2 說它買到 0 或過強 |
| 多格推撞 | ❌ 不需要 | 會變 | ⚠️ 必須先回答 R-TERR-07 的「停下來那一格」語意（§1.3） |
| ZOC | ✅ **需要**（控制區是衍生量，但會改變 `ReachableCells`） | 🔴 大幅變動 | 高 —— [H20](NOTE-2026-08-15-移動力射程與地圖幾何.md) 紙上模型都還沒做 |

> 🟡 **建議順位：連鎖推撞 > 其餘全部。** 它零新狀態、可證明終止、不受整除性懲罰，
> 而且是唯一能同時提升擊退價值與正守/桃太郎防守價值的改動。

### Q3：無 ZOC 下，純佔位阻擋能不能撐起正守與桃太郎的防守價值？

> 🟡 **能，但只在 W=1 的地圖上，而且價值是全有全無的。**
>
> - ✅ **W=1**：正守封鎖 7.5 回合（Guard 後 14.5），是影丸的 5 倍。**這是真實且巨大的價值。**
> - 🔴 **W≥2 且只投入 1 人**：延後**恰好 0 回合**。敵人免費走過。
> - 🔴 **W≥3**：封鎖需要 75% 的隊伍，實務上不可行。
>
> **所以防守價值目前是地圖屬性，不是角色屬性。**
> 要讓它變成角色屬性，需要的是 ZOC（H20），不是更多 HP 或 DEF。
>
> 🟢 這與 [strategy-depth-plan §1.4](06-validation/strategy-depth-plan.md) 的
> 「ZOC ❌ 前排保護不了後排」是同一件事，本檔補的是**量化**：
> **前排在 W=1 保護 7.5 回合，在 W=2 保護 0 回合。**

# 6. 🔴 確認的缺陷：擋住增援點會使戰鬥永遠不結束

🟢 **證據鏈**（三處程式碼，本會話逐條讀過）：

```csharp
// BattleSimulator.cs:733-734
if (r.Spawned || r.Faction != faction || r.Turn != state.TurnIndex) continue;
if (!state.CanUnitEnter(r.Position)) continue;   // ← 註解：「blocked this turn; try again next round」

// BattleState.cs:275-280
public bool HasPendingReinforcements(Faction f) {
    for (...) if (!_reinforcements[i].Spawned && ... == f) return true;   // ← 只看 Spawned，不看 Turn
    return false;
}

// BattleSimulator.cs:825
if (state.CountLiving(Faction.Enemy) == 0 && !state.HasPendingReinforcements(Faction.Enemy))
```

**故障序列**：

| # | 事件 |
|---|---|
| 1 | 增援宣告於回合 `N`、位置 `P` |
| 2 | 回合 `N` 的敵方階段開始時，**任何活著的單位**（含敵方自己）站在 `P` |
| 3 | `CanUnitEnter(P) == false` → `continue` → `r.Spawned` **維持 false** |
| 4 | 回合 `N+1`：`r.Turn != TurnIndex` → `continue` → **永遠不再嘗試** |
| 5 | `HasPendingReinforcements(Enemy)` **永遠回傳 true** |
| 6 | 🔴 **玩家殺光所有敵人，`BattleEnded` 永不產生。R-WIN-04 明文無回合上限、無平手 —— 規則層沒有逃生口** |

**為什麼註解與程式碼不一致**：註解描述的行為需要第一行改成 `r.Turn > state.TurnIndex`
或把 `r.Turn` 往後推一回合。**目前兩者都沒有做。**

**觸發機率不低** 🟡：
🟢 目前只有 2 張地圖用 `spawn turn=N`，但跑分工具有 **15% 均勻雜訊**，
而 R-TERR-09 的註解已經指出均勻雜訊會把單位送到不該去的格子。
且敵方 AI 自己也會經過增援格 —— **`CanUnitEnter` 不區分陣營。**

> ⚠️ **本檔不修改任何程式碼，也不裁決修法。**
> 這是回報。已另開任務單獨追。
> 🟢 短期規避見 §5.2 的 **G4**。
