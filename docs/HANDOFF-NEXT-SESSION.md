### 2.12 玄真技能的可算門檻 `[A]`

`[A]` 由 `units.txt` 核對：玄真 ATK 90，`kohaku_3hit` DEF 20 / HP 120。
→ 每刀 `max(1, 90−20) = 70`，`ceil(120/70) = 2 刀`。

`[A]` **要壓成 1 刀需要單次傷害 ≥ 120**（即 ATK ≥ 140，或倍率使單次輸出達 120）。

## 5. 已知的儀器限制（全部要跟數字一起讀）

### 5.1 腳本策略不會為了打砲塔而前進 `[A]`
無 clock 版本 33% 場次撞到 60 回合安全網。**`gym-opening` 的核心決策（何時進場）現有策略全都不做。**

### 5.2 沒有任何策略會「一邊路由一邊保持節奏」 `[A]`
`shield-wall` 是最接近的嘗試，比不擺陣型差 23–26 點。
`[C]` **這是第六次「機制有了、好的使用者沒有」**（反擊、淨化、控制技能、斬首、防禦、陣型）。

### 5.3 雜訊會被合法指令集的大小污染 `[A]` —— **已由程式碼確認**

`SimulationRunner.Decide`：
```csharp
if (rng.Chance(config.NoisePercent)) {
    List<ICommand> legal = LegalCommands.For(state, unit);
    if (legal.Count > 0) return legal[rng.NextInt(legal.Count)];
}
return config.Strategy.DecideNext(state, unit, rng);
```

`[A]` 均勻抽樣，而 `LegalCommands.For` 依 AP 過濾技能
→ **技能成本改變會改變 `legal.Count` → 改變雜訊分布 → 連不使用技能的策略也受影響。**

`[A]` 實證：成本掃描中 `corridor-hold` 應該是平的，實際在 **48–58%** 之間晃。

> **所以不要拿同一列的 `corridor-hold − control-hold` 當精確的 treatment effect。**
> **要跨列比較 `control-hold` 的 response curve。**

### 5.4 求解器是單步前瞻 ＋ 策略推演，不是完整博弈樹 `[A]`
數字的意思是「假設後續由 `corridor-hold` 接手，第一步最好下哪」。
**不能用它宣稱「玩家需要三回合 planning」。**

### 5.5 M3 目前是壞的 `[A]`
19–20 回合，目標 6–10。**冷卻／次數限制在 M3 修好之前都不該碰**
（[判準 5](NOTE-2026-08-15-技能機制與數值-關卡的分工.md)：那要戰鬥夠長才是旋鈕）。

### 5.6 真人 playtest 仍然只有一句話 `[A]`
「移動到小怪 4 格附近等他靠近，接著下回合兩刀劈死。保留跟不保留都差不多。」
`[A]` 64 個 encounter、193 個測試，而**結構化的真人 playtest 一次都沒做過**。

### 5.7 攻擊射程無視牆壁 `[A]` —— **已由程式碼確認**

`BattleQueries.AttackableTargets`：

```csharp
if (state.Map.Topology.Distance(attacker.Position, other.Position) <= attacker.Def.AttackRange)
```

> 威脅圈是真的，但本來應該塑形它的牆不存在。

### 5.8 M6 的百分比是**條件分布** `[A]`

`[A]` M6 只算「有穿越的場次」。D1 那三張圖的穿越率是 99 / 63 / 100（每張 200 場）。

> **穿越率差 18 點就等於分母換了一群場次，兩張圖的 M6 直方圖不能直接相減。**
> `[A]` D1 的 F3 那一組不受影響（99 對 100），**壞掉的是中間那一階。**

### 5.9 兩邊擠同樣的缺口時，局部地形編輯**不是局部的** `[A]`

### Unity 外（`dotnet` 可用，Core/Sim 零引擎依賴）

scratchpad 內建臨時專案（**不在版控，需要時重建**）。本輪四個都驗證過：

| 要做的事 | 怎麼做 |
|---|---|
| 跑分 | console 專案 `ProjectReference` 到 Core ＋ Sim |
| **跑 EditMode 測試** | Core / Sim 各一個 class library（**AssemblyName 要正確**，否則 A1 失敗），測試專案用 **NUnit 3.14**，另補 ~50 行的 `UnityEngine.TextAsset` / `Resources` shim |
| 驗證 Unity 層編譯 | netstandard2.1，`Reference` 指向 `...\Editor\Data\Managed\UnityEngine\*.dll` ＋ `Library\ScriptAssemblies\Unity.InputSystem.dll`。**Core 要用 `Compile Include` 併進來**（Core 專案是 net8.0，NuGet 不讓 netstandard2.1 參考） |

`[A]` **2026-08-16 重建時多踩到的三個坑，寫下來省下一次的時間**：

| 症狀 | 原因與解法 |
|---|---|
| `DataTests` 十個測試全部 `ArgumentNullException (path1)` | `[SetUpFixture]` **只作用於它自己的命名空間與其下層**。放在 `Ediki.Tests.Harness` 對 `Ediki.Tests` 的測試無效。**放在全域命名空間**（不包在任何 `namespace` 裡） |
| `error CS1529: using 必須位於所有命名空間定義之前` | 同一個 shim 檔前面已經有 `namespace UnityEngine`。**用完整限定名 `[NUnit.Framework.SetUpFixture]`**，不要在檔尾補 `using` |
| Unity 層 `CS0012: PreserveAttribute 定義在未參考的組件中` | Unity 6000.5 把它移到 **`Unity.Scripting.dll`**，不在 `UnityEngine*.dll` 的 glob 裡。明確加一行 `Reference` |

`[A]` shim 找資料夾的方式：csproj 用 `AssemblyMetadataAttribute` 把專案路徑烤進組件，
shim 用反射讀回來 —— **不必設環境變數，從任何工作目錄都跑得動**。

> **每個 csproj 要放各自的資料夾** —— 同層多專案會共用 `obj/`，NuGet 的 `project.assets.json` 會互相覆蓋。
>
> ⚠️ **跑分批次已經大到會超時**（~25 地圖 × 6 策略 × 200 場 > 10 分鐘）。
> 針對單一問題時請自建**只含相關地圖與策略**的精簡 driver。
> `[A]` D1 那個 driver 是 3 地圖 × 3 策略 × 200 場，**不到一分鐘**。
>
> `[A]` **driver 值得多寫一個 `routes` 模式**：把其他缺口封死，逐條量
> 「玩家 spawn → 該缺口 → 打得到敵人的位置」的 AP，**兩邊都量**。
> 目測路線成本會錯，而且看不到「敵人也走同樣的缺口」（§5.9）。

### golden hash

改 Core 之後 **A4 一定會失敗** —— 那是它該有的行為。
先問「這次改動應該改變模擬結果嗎」，再更新常數。流程見
[05-development/workflows.md §6](05-development/workflows.md)。

**本輪加了一個勝利條件、三個技能、兩個狀態欄位，A4 一次都沒有失敗。**
做法是**新欄位只在被用到時才折進雜湊**（沿用污染陣列那一套）。**新增規則時請照這個模式。**

`[A]` **D1 那一輪也沒有動到 A4** —— 技能動作分類只改 `Ediki.Sim`，規則層一個字都沒碰。
**量測儀器的改動不應該讓 A4 失敗；如果失敗了，那代表你不小心改到規則層。**
