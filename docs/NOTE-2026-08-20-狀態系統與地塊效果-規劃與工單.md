## 1. 現況調查（證據，非推測）

### 1.1 Core 已經有的「狀態」機制

不是沒有，是**有四個各自為政的特例**：

| 機制 | 存在形式 | 檔案 |
|---|---|---|
| 格擋 | `UnitState.IsGuarding`（bool，下回合清除） | `BattleSimulator.ExecuteEndTurn` |
| 緩速 | `UnitState.SlowedUntilTurn`（回合戳記） | `BattleState.IsSlowed` |
| 引誘 | `UnitState.TauntingUntilTurn` | `BattleState.IsTaunting` |
| 破甲 | `UnitState.ArmorBrokenUntilTurn` ＋ `ArmorBrokenAmount` | `BattleState.EffectiveDef` |
| 穢氣 | `BattleState._contamination`（每格一個 int） | `BattleState.AddContamination` |

**共通手法**：`XxxUntilTurn` 是回合戳記，`TurnIndex <= stamp` 即為生效。
不需要每回合遞減，**自己會過期**。

### 1.2 「加狀態但不動 A4」的手法已被證明四次

`BattleState` 有四個 gate：`HasContamination` / `HasControlStatus` /
`HasArmorBreak` / 每回合上限。`StateHasher` 只在 gate 為真時才把那一段折進雜湊。

程式碼裡的原話：

> new state costs the golden constants nothing until it is used.

**這就是這次要沿用的樣板。** 只要沒有任何單位中毒，雜湊就與現在逐位元相同，
A4 三個常數（`3080245196` / `3711821134` / `1561619701`）不動。

### 1.3 傷害管線的掛載點

```
BattleSimulator.ExecuteAttack
  └─ BattleRules.ComputeDamage(
         a.Def.AtkOnRound(turn),      ← 攻擊方數值，加傷要掛這裡
         next.EffectiveDef(t),        ← 防禦方數值，破甲已經掛在這裡
         t.IsGuarding, rules.Damage)
```

`EffectiveDef` 已經是「基礎值 ± 狀態」的樣子。**缺的是對稱的 `EffectiveAtk`。**

### 1.4 回合邊界（中毒要在這裡跳）

`BattleSimulator.ExecuteEndTurn`，`upcoming == Faction.Player` 時：

```csharp
next.TurnIndex++;              // 一個完整回合 = 我方 + 敵方
SpreadContamination(next, log); // 每回合一次的既有 tick
```

**中毒／流血的扣血就掛在 `SpreadContamination` 旁邊。**
註解已寫明為何在這裡：per phase 會讓速率平白加倍。

### 1.5 TerrainDef 目前只有 5 個欄位

`Index` / `Name` / `Symbol` / `MovementCostHundredths` / `BlocksMovement` / `IsLethal`。

`terrain.txt` 的檔頭寫著：

> Keep this list small. Do not add terrain types without a decided requirement.

—— 指的是不要亂加**地形種類**，不是不能加**欄位**。但這條註解代表加欄位也該有裁決。

> **不要直接做 —— 登錄成 Open Decision 交給企劃裁決。**

**你就是裁決者，所以這件事可以做 —— 但流程要走完。**
本文件第 3 節就是那份 OD 的內容，裁決後請登錄進 `OPEN-DECISIONS.md`
並更新 charter §4（劃掉該列並註明裁決日期），否則下一個人會依 charter 把它擋回去。

### 2.2 🔴 GDD 的狀態是機率性的，規則層是決定論的

GDD 原文：「30% 暈眩」「50% 機率免疫」「隨機賦予負面狀態」「隨機從狀態池中附帶 2 種」。

但 `ADR-0003` 與 determinism rule 1 要求規則層**完全決定論、整數運算、無擲骰**，
`OD-05` 也明確裁掉了命中／閃避骰。`Ediki.Sim` 的 `DeterministicRandom`
自述是「a SAMPLING device, **not a gameplay rule**」。

**這兩者不能同時成立。** 三條路：

- **(a) 狀態一律必中** —— 命中就附加，機率欄位不做。規則層不變，最省。
- **(b) 用「累積門檻」取代機率** —— 例如「連續被打 3 次才暈眩」。決定論，且比骰子好調。
- **(c) 在 `BattleState` 塞一個 seeded RNG** —— 忠於 GDD，但 `StateHasher` 要納入
  RNG 狀態、A4 三個常數全部作廢、replay 與 SquadMatrix 的可重現性要重新驗證。
  **這是本文件裡唯一會炸掉 A4 的選項。**

### 2.3 🟡 Core 既有機制與 GDD 同名但不同義

| GDD | Core 現況 | 一樣嗎 |
|---|---|---|
| 緩速 SLOW：移動成本 **× 2** | `SlowCommand`：每格 **+1 AP** | ❌ 不同公式 |
| 虛弱 FRAIL：DEF **× 0.70** | 破甲：DEF **− 20**（資料可調） | ❌ 乘法 vs 減法 |
| 強壯 MIGHT：ATK **× 1.30** | 無 | — |

乘法在整數規則層是可行的（`atk * 130 / 100`，截斷），但**乘法與減法在數值設計上是
兩件事** —— 破甲對高 DEF 單位效果固定，虛弱對高 DEF 單位效果更強。

已量測的結論（`units.txt` 註解）：破甲的價值在於**跨過刀數階梯**，而刀數階梯是懸崖
（2 刀 68%、3 刀 1%）。換成乘法會改變它跨不跨得過去。**所有既有的破甲量測會失效。**

### 2.4 🟡 狀態沒有來源

現在沒有任何東西會施加狀態。要能用，至少需要一個來源：

- **地形**：站上去中毒（這正好接上「地塊數值效果」那一半）
- **技能**：新增技能，或讓既有技能附帶狀態
- **攻擊附帶**：`unit` 資料加 `onHitStatus=poison`
- **敵人被動**：晦氣「攻擊附帶中毒」（GDD 472 行）

> 每一題我都給了建議。**建議不是決定** —— 沒有你的答覆，Codex 不該自行選擇。

### Q1. charter 否決權：正式解除嗎？

- **建議**：解除，範圍限定在「本文件列出的狀態」，並在 charter §4 註明
  「2026-08-20 裁決，改為 Stage 01 範圍內」。
- 不解除的話，這整份工單作廢。

### Q2. 機率怎麼處理？（§2.2）

- **建議：(a) 一律必中。** 理由：保住 A4、保住 replay、保住 `SimulationRunner`
  的可重現性，而且**必中的狀態比機率狀態好調平衡** —— 企劃調的是持續回合數與
  數值，不是骰面。GDD 的 30% 之類等到有 RNG 架構決策時再說。
- 選 (c) 的話請先單獨開一個 OD，那是比狀態系統本身更大的架構決定。

### Q3. 這一輪做哪幾個狀態？

GDD 的 8 個 General Status ＋ 流血。建議切成兩批：

| 批次 | 狀態 | 為什麼 |
|---|---|---|
| **第一批（建議本輪）** | 中毒 POISON、流血 BLEED、強壯 MIGHT、脫力 WEAKEN、固元 FORTIFY、虛弱 FRAIL | 全部是「每回合扣血」或「數值乘法」兩種模式，共用同一套機制 |
| **第二批（建議延後）** | 暈眩 STUN、加速 HASTE、緩速 SLOW | 暈眩要動回合流程與 AI；加速／緩速與既有 `SlowCommand` 直接衝突（§2.3） |

- **建議**：本輪只做第一批。第二批各自都會動到回合流程或推翻既有量測。

### Q4. 「加傷」指哪一個？

你說的「加傷效果」在 GDD 裡有兩個候選，方向相反：

- **強壯 MIGHT**：自己 ATK × 1.30（我方變強）
- **虛弱 FRAIL**：目標 DEF × 0.70（敵人變脆）

GDD **沒有**「易傷（受到傷害 ×1.3）」這個狀態。

- **建議**：兩個都做（同一套乘法機制，成本幾乎為零），由你在編輯器裡挑著用。

### Q5. 破甲要不要改成虛弱？（§2.3）

- **建議：不要改，兩者並存。** 破甲是「DEF −N」，虛弱是「DEF ×0.7」，
  在編輯器裡是兩個不同欄位。理由：破甲有已發表的量測，改公式會讓那些數字失效；
  而且減法與乘法在設計上本來就是兩種工具。
- 若你要統一成 GDD 版，請明說 —— 那要重跑 `gym-crucible-armor` 的基線。

### Q6. 緩速：Core 版還是 GDD 版？

- **建議：本輪不碰**（見 Q3 第二批）。既有 `SlowCommand`（+1 AP/格）有量測基線，
  GDD 版（×2 成本）是不同機制。等 Q3 第二批再處理。

## 4. 建議架構（在上述建議答案成立的前提下）

### 4.1 狀態的形狀

**不要**每個狀態一個 `int` 欄位。六個狀態就是六個欄位、六個 gate，
而 `UnitState.Clone()` 是手寫的（`ADR-0004`），每加一欄就多一個漏抄的機會。

**建議**：一個小的值型別陣列。

```csharp
// Ediki.Core/Status.cs  （新檔）
public enum StatusKind
{
    None = 0,
    Poison = 1,     // 每回合失去 MaxHp 的 N%
    Bleed = 2,      // 每回合失去 MaxHp 的 N%（與中毒同機制，不同來源與數值）
    Might = 3,      // ATK x N%
    Weaken = 4,     // ATK x N%
    Fortify = 5,    // DEF x N%
    Frail = 6       // DEF x N%
}

/// 一個生效中的狀態。UntilTurn 是回合戳記，與 SlowedUntilTurn 同一套語意。
public readonly struct ActiveStatus
{
    public readonly StatusKind Kind;
    public readonly int UntilTurn;
    public readonly int Magnitude;   // 百分比。中毒=每回合扣的 MaxHp%；強壯=130
}
```

`UnitState` 加**一個**欄位：`List<ActiveStatus> Statuses`（沒有狀態時為 `null`）。

- `Clone()` 只多一行（null 時保持 null）
- `BattleState.HasStatuses` 一個 gate
- `StateHasher` 一個 gated 區塊

> ⚠️ **順序必須是決定論的。** 折進雜湊前要依 `(Kind, UntilTurn, Magnitude)` 排序，
> 或保證加入順序本身是決定論的。這是這個設計唯一的新風險，測試要專門蓋它。

### 4.2 數值怎麼生效

```csharp
// BattleState，與既有 EffectiveDef 對稱
public int EffectiveAtk(UnitState u, int turnIndex)
{
    int atk = u.Def.AtkOnRound(turnIndex);
    atk = atk * PercentOf(u, StatusKind.Might) / 100;   // 無狀態時為 100
    atk = atk * PercentOf(u, StatusKind.Weaken) / 100;
    return atk < 0 ? 0 : atk;
}
```

`EffectiveDef` 同樣掛上 Fortify / Frail，**破甲的減法保留在最後**（先乘後減）。

> **乘法順序要寫進規格。** `(ATK×1.3)×0.7` 與 `ATK×(1.3×0.7)` 在整數截斷下不同。
> 建議：**依 `StatusKind` 列舉順序逐一套用，每步截斷** —— 可預測、可手算、可測。

### 4.3 每回合扣血

掛在 `ExecuteEndTurn` 的 round boundary，`SpreadContamination` 之後：

```csharp
TickDamageOverTime(next, log);   // 中毒、流血
```

規則要寫死的三件事：

1. **順序**：依 `UnitState.Id` 遞增（決定論）
2. **會不會致死**：建議**會**，且要走既有的死亡判定（不要另開一條路）
3. **傷害下限**：`MaxHp * pct / 100`，最少 1（與 `RestHealAmount` 同慣例）

### 4.4 來源（本輪只做兩個）

| 來源 | 資料 | 說明 |
|---|---|---|
| **地形** | `terrain.txt` 新欄位 | 站在上面的單位每回合獲得該狀態，1 回合（離開就自然過期） |
| **攻擊附帶** | `units.txt` 新欄位 | 命中時附加，必中（Q2 建議 a） |

技能施放狀態、敵人被動**本輪不做** —— 那要新的 Command，屬於「新增系統」流程。

## 5. 資料格式

### 5.1 `terrain.txt` 新增欄位（全部可選，省略即為 0／無）

```
terrain name=Swamp symbol=m cost=3 blocks=false
        status=poison statusPercent=10 statusTurns=1
        damagePerTurn=0 atkPercent=100 defPercent=100
```

| 欄位 | 意義 | 預設 |
|---|---|---|
| `status` | 站上去附加的狀態名 | 無 |
| `statusPercent` | 該狀態的數值（中毒=每回合 MaxHp%） | 10 |
| `statusTurns` | 持續回合 | 1 |
| `damagePerTurn` | 直接扣血（不經狀態），MaxHp 的 % | 0 |
| `atkPercent` / `defPercent` | 站在上面時的數值倍率 | 100 |

> **相容性**：所有欄位可選，現有 `terrain.txt` 一個字都不用改，行為逐位元不變。

### 5.2 `units.txt` 新增欄位

```
unit id=huiqi ... onHitStatus=poison onHitPercent=10 onHitTurns=2
```

### 5.3 狀態本身要不要資料驅動？

**建議：不要。** 六個狀態是 GDD 已封板的封閉集合，把它們做成 `StatusKind` 列舉
比做成一張可擴充的表更誠實 —— **數值可調，種類不可憑空新增**（新種類要新規則，
走「新增系統」流程）。這與 `ObjectiveKind` 的處理一致。

## 6. 編輯器要加什麼

### 6.1 新增「地形」編輯分頁

目前編輯器**只能選地形，不能改地形**。要加一個可編輯 `terrain.txt` 的面板：

- 列出所有地形，可改：中文顯示名、移動消耗、是否阻擋、是否致命
- 新增：附加狀態（下拉）、數值、持續回合、每回合扣血、ATK／DEF 倍率
- **企劃模式用中文**：「泥沼 — 移動消耗 3、站著每回合中毒 10%」

> ⚠️ **改地形是全域的**，和改 `units.txt` 一樣會影響所有既有關卡。
> **必須沿用 `UnitVariantWriter` 已經確立的做法**：改動產生**新的地形項目**
> 而不是覆寫既有列，否則 64 個既有 encounter 的量測基線會一起漂移。
> 這一點請 Codex 特別注意 —— 它是本工單最容易做錯的地方。

### 6.2 單位面板新增「攻擊附帶狀態」

放在既有「技能」區塊下面，沿用 `UnitStatBlock` 的 pending-edit 機制
（改了會產生新的 unit 變體，不覆寫原列）。

### 6.3 地圖上要看得見

`PrototypeVisuals` 已經是編輯器與遊戲共用的視覺文法。加：

- 有附加狀態的地塊 → 地面加一個小圖示或第二層色帶
- 中毒中的單位 → 沿用既有狀態染色（`SlowColor` / `TauntColor` 那一組）

## 7. 測試與 A4 保護（**這一節不可協商**）

| 測試 | 為什麼 |
|---|---|
| **A4 三個常數不變** | 沒有任何單位帶狀態時，雜湊必須逐位元不變。這是整個 gated-fold 設計的唯一驗收 |
| 狀態折入雜湊的順序是決定論的 | §4.1 唯一的新風險。同一組狀態以不同順序加入，必須得到相同雜湊 |
| 既有 64 個 encounter 全部照常載入 | `DataTests` 已有，新欄位可選就會自動通過 |
| 中毒可以致死，且走既有死亡判定 | 否則會出現 HP≤0 卻還活著的單位 |
| 乘法順序固定且可手算 | `(ATK×1.3)×0.7` 的截斷結果要寫成常數斷言 |
| 狀態過期不需要 tick | 回合戳記語意，與既有 Slow 一致 |
| `terrain.txt` 全欄位往返無損 | 沿用 `UnitStatBlock` 的往返測試手法 |
| 編輯器改地形產生新項目、不覆寫舊列 | §6.1 的風險 |

**A4 若失敗，先問「這次改動應該改變模擬結果嗎？」**（`workflows.md §6`）。
本工單的答案應該是**不應該** —— 沒用到狀態的場地不該有任何變化。
**A4 紅了代表 gate 沒做好，不要更新常數。**
